# Practica1-SO
Práctica 1 de sistemas operativos desarrollada en github codespaces 
El proyecto Taller 1 de Sistemas Operativos implementa una arquitectura de comunicacion entre procesos independientes utilizando el lenguaje C sobre el sistema operativo Linux. En esta arquitectura, el archivo de cabecera comun.h cumple el rol fundamental de compartir funciones, librerias y estructuras de datos entre los diferentes archivos de codigo fuente. Antes de la ejecucion, el sistema genera una copia de este archivo dentro de cada modulo .c para garantizar que todos los componentes operen bajo las mismas reglas. De esta forma, comun.h actua como un traductor de bytes entre los procesos cliente y servidor, asegurando una interpretacion uniforme de los mensajes ya sea que la comunicacion se realice mediante tuberias nombradas de tipo FIFO o mediante memoria compartida. Para evitar la inclusion multiple de las mismas definiciones en el programa, se emplea la directiva de preprocesamiento ifndef, la cual comprueba que no exista una definicion previa y permite que el compilador procese el contenido de la cabecera únicamente cuando no ha sido cargado con anterioridad.



El preprocesador de C cumple cuatro tareas esenciales antes de que el codigo sea transformado a lenguaje binario por el compilador: reemplazar las macros definidas mediante define por sus valores correspondientes, incluir el contenido de los archivos de cabecera solicitados con include, evaluar bloques de compilacion condicional como ifndef e ifdef, y eliminar los comentarios explicativos para optimizar espacio. El uso de la directiva define para crear constantes no consume memoria RAM durante la ejecucion del proceso, debido a que el preprocesador realiza una sustitucion directa de texto previa a la compilacion. Dentro de estas constantes se define la ruta de las tuberias nombradas en el directorio /tmp del sistema operativo. El directorio /tmp reside directamente en la memoria RAM y otorga permisos globales de lectura y escritura a todos los archivos alojados en el, lo que garantiza una transferencia de datos fluida y previene errores o bloqueos por permisos durante la comunicacion.



En el entorno del Kernel de Linux, cada proceso en ejecucion cuenta con un espacio de memoria virtual completamente aislado, por lo que un proceso no puede acceder ni escribir directamente en la memoria de otro sin provocar un error de segmentacion. Para superar este aislamiento, el sistema operativo provee los mecanismos de comunicacion entre procesos conocidos como IPC. Dentro del intercambio de datos a traves de tuberias y archivos en Linux, el sistema operativo garantiza la propiedad de atomicidad siempre que el tamaño del archivo o mensaje sea menor a 4096 bytes. Esto asegura que la informacion se envie de golpe en una sola operacion continua, sin mezclarse con las peticiones de otros procesos. Para el transporte intermedio de estos datos, se utilizan buferes, los cuales funcionan como recipientes temporales en la memoria RAM destinados a almacenar caracteres mientras se transfieren de un punto a otro durante su procesamiento.



El protocolo de comunicacion entre procesos utiliza estructuras compuestas en C definidas mediante typedef enum y typedef struct. La construccion typedef enum permite asociar cadenas de caracteres a valores enteros numericos, delimitando la cantidad de opciones validas en el programa. Por su parte, typedef struct agrupa distintas variables en un contenedor unico para transmitirlas en una sola operacion. En la estructura del programa existen dos structs principales denominados Solicitud y Respuesta. La estructura Solicitud contiene un elemento de tipo TipoBusqueda para indicar la opcion seleccionada por el usuario y un arreglo de caracteres del tamaño del bufer para almacenar la caracteristica del vehiculo a consultar. La estructura Respuesta contiene un arreglo de caracteres que transporta el resultado generado por el servidor y una variable que funciona como bandera para notificar al cliente si la busqueda ha concluido o si el servidor continua procesando datos.



La lectura de las opciones del usuario se gestiona mediante la funcion scanf dentro de un bucle infinito guiado por la condicion while(1). Debido a que scanf opera directamente sobre la memoria RAM, requiere recibir la direccion de memoria de la variable de destino. Si se intentara pasar una variable sin especificar su direccion, el programa tomaria su valor numerico como una direccion real de memoria, provocando un fallo de segmentacion. Toda la informacion tecleada viaja inicialmente al bufer de entrada stdin administrado por el Kernel de Linux y la libreria estandar de C conocida como glibc, la cual viene empaquetada con el compilador gcc. Cuando el usuario introduce una opcion invalida, scanf falla y la libreria glibc retorna un valor de cero. Si este bufer stdin no se limpia, los caracteres no procesados permanecen congelados en la RAM, haciendo que el programa quede atrapado en un bucle infinito. Para solucionar esto, el programa utiliza la funcion getchar dentro de un bucle para extraer individualmente cada caracter del bufer stdin hasta encontrar un salto de linea, seguido de una llamada adicional a getchar para eliminar el salto de linea remanente.



La interaccion con la entrada y salida de datos sigue una jerarquia estructurada que va desde las funciones de alto nivel de glibc como scanf hasta las llamadas al sistema POSIX de bajo nivel como read, las cuales solicitan la ejecucion al Kernel de Linux a traves de la rutina sys_read y los controladores del teclado. Las funciones de alto nivel utilizan convertidores de texto internos denominados parsers para transformar cadenas de caracteres ASCII en valores binarios almacenables en la RAM. Para establecer mecanismos de comunicacion por memoria compartida de forma segura entre procesos aislados, se emplean los parametros SHM_KEY_PATH y SHM_PROJ_ID en conjunto con la funcion ftok. Esta funcion ejecuta un algoritmo matematico que toma el numero de i-nodo de la ruta indicada y un identificador caracter de ocho bits para calcular una clave IPC entera y unica. Al compartir los mismos parametros, ambos procesos independientes obtienen la misma clave IPC para enlazarse exitosamente a la misma region de memoria.



La sincronizacion en la memoria compartida se realiza mediante semaforos POSIX nombrados, los cuales se administran en la subcarpeta /dev/shm dentro del sistema de archivos volatil tmpfs alojado directamente en la memoria RAM. La ubicacion en RAM de /dev/shm garantiza que las operaciones de sincronizacion se ejecuten con latencias casi nulas en el orden de los nanosegundos, evitando los cuellos de botella que provocaria la lectura en almacenamiento fisico. Internamente, un semaforo POSIX no es un archivo de texto sino una estructura del Kernel provista de un contador atomico y una cola de espera. Cuando el contador del semaforo se encuentra en cero y un proceso ejecuta la instruccion sem_wait, el Kernel cambia el estado de dicho proceso a estado de reposo TASK_INTERRUPTIBLE y el planificador de tareas lo remueve de la CPU. Esto evita el consumo inútil de ciclos de procesamiento por espera activa y protege la integridad de los datos ante posibles condiciones de carrera. Finalmente, la naturaleza volatil de la memoria RAM asegura que ante cualquier interrupcion abrupta del sistema no queden archivos ni registros corruptos almacenados en el disco duro.




Para realizar la observacion y auditoria del sistema operativo durante la ejecucion del proyecto, se utilizan diversas herramientas por consola sobre Linux. La identificacion de los procesos en ejecucion, junto con sus identificadores PID y PPID asociados a la shell madre, se realiza mediante el comando ps -f -C servidor -C clienteFifo -C clienteShm, o de forma jerarquica visualizando el arbol de procesos con pstree -p | grep -E "servidor|cliente". Para rastrear el comportamiento interno y las llamadas al sistema operativo de bajo nivel como read, write u open, se ejecuta el comando strace ./clienteFifo. En situaciones donde alguno de los procesos se encuentra en estado de bloqueo esperando un recurso IPC o una lectura en la tuberia, es posible examinar la funcion exacta del Kernel donde se halla detenido y su estado mediante el comando ps -o pid,ppid,stat,wchan,cmd -C clienteFifo -C clienteShm. Asimismo, para simular fallos y observar el comportamiento colateral ante la terminacion inesperada del servidor, se induce su caida con el comando pkill -9 servidor, lo que provoca que el cliente reciba un error de tuberia rota EPIPE o quede bloqueado en el semaforo. Finalmente, para identificar recursos IPC huerfanos dejados en la memoria RAM tras una finalizacion abrupta, se inspecciona la memoria compartida con ipcs -m, los semaforos POSIX con ls -l /dev/shm/ y los archivos de tuberia con ls -l /tmp/fifo_*, procediendo a su liberacion manual mediante rm -f /dev/shm/sem.sem_* y rm -f /tmp/fifo_*, la llamada ipcrm -m id_memoria, o de manera automatizada ejecutando el comando make clean.
